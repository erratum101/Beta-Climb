# Beta Climb

Прототип сохраняет профиль скалолаза и разбирает видео одной попытки. Через мобильный интерфейс можно загрузить ролик, закрыть приложение, затем открыть разбор в истории и перейти от совета к соответствующему моменту видео.

## API и интерфейс

Команды ниже выполняются из корня репозитория. Нужны Docker с Compose v2, PostgreSQL, приватный S3-совместимый бакет и доступ к модели через Eliza. Для локального воркера нужны Python 3.12, Poetry 2 и FFmpeg с `ffprobe` и кодеком `libx264`.

1. Создайте локальный `.env` по [шаблону](.env.example). Укажите доступ к бакету и `MEMORY_ELIZA_OAUTH_TOKEN`. Маршрут Eliza и модель `glm-5.3-flash` уже заданы в шаблоне.
   Для этой модели воркер задаёт `LLM__REASONING_EFFORT=low`. Доступны также `high` и `max`. [Параметры Z.ai](https://docs.z.ai/api-reference/llm/chat-completion)
2. Заполните `docker/.env.managed` по [примеру PostgreSQL](docker/.env.managed.example). Пользователю БД нужны права для миграций в схеме `betaclimb`. На хосте Compose ожидает сертификат PostgreSQL в `~/.cloud-certs/root.crt`. Внутри контейнера тот же файл доступен по пути `/certs/root.crt`.
3. Соберите и запустите API и UI. На macOS с отдельно установленным Homebrew Compose замените `docker compose` на `docker-compose`, если плагин недоступен в Docker CLI.

```sh
docker compose --env-file .env -f docker/docker-compose.yml up -d --build api frontend
docker compose --env-file .env -f docker/docker-compose.yml ps
```

При запуске API Flyway применяет миграции в `betaclimb`. [V5](backend/migrations/V5__video_pipeline.sql) расширяет существующие таблицы `videos` и `tasks` полями владельца, снимка профиля, результата и аренды задачи. Для хранения исходников и результатов API и воркер должны использовать один бакет, а для очереди — одну схему PostgreSQL.

## Python-воркер

В отдельном терминале, начиная из корня репозитория, установите окружение из `backend/worker/poetry.lock`. Следующие команды рассчитаны на macOS/Linux.

```sh
cd backend/worker
poetry env use 3.12
poetry install
ffmpeg -version
ffprobe -version
```

В `MODELS_DIR` передаётся папка с тремя файлами весов — `holds.pt`, `mobile_sam.pt` и `pose_landmarker_heavy.task`. Можно указать абсолютный путь к уже скачанной папке `web_services/ratpoc/assets/models`. Для новой копии проекта скрипт RatPoC скачает веса и три размеченных демонстрационных ролика. Адреса источников и контрольные суммы SHA-256 приведены в [манифесте](frontend/ratpoc/sources.json).

```sh
poetry run python ../../frontend/ratpoc/fetch_assets.py
```

Запустите воркер из той же папки `backend/worker`. Все настройки воркер читает из окружения. `ENV_FILES` перечисляет dotenv-файлы через двоеточие, уже экспортированные переменные имеют приоритет. `PGSSLROOTCERT` указывает путь на хосте и заменяет путь контейнера в строке подключения. `CONCURRENCY=1` ограничивает этот процесс одним одновременно исполняющимся этапом. На машине с достаточной памятью значение можно увеличить для обработки независимых задач.

```sh
DB_SCHEMA=betaclimb PGSSLROOTCERT="$HOME/.cloud-certs/root.crt" \
  ENV_FILES=../../.env:../../docker/.env.managed \
  MODELS_DIR=../../frontend/ratpoc/assets/models CONCURRENCY=1 \
  poetry run python -m core.worker
```

## Разработка с локальными PostgreSQL и S3

Для запуска на своём компьютере подойдут PostgreSQL и S3-совместимый сервер на loopback. В сквозных тестах использовались PostgreSQL 16 и Moto. Проще всего использовать хостовые процессы для API, S3 и воркера, чтобы подписанные ссылки на видео открывались по тому же адресу и в браузере.

1. Поднимите PostgreSQL из профиля `local-db` и эмулятор S3. Из корня проекта выполните `docker compose -f docker/docker-compose.yml --profile local-db up -d db`. В отдельном терминале запустите `uvx --from 'moto[server]' moto_server -H 127.0.0.1 -p 5005`.
2. Установите следующие переменные в терминалах API и воркера. Они соответствуют локальному контейнеру PostgreSQL и одноразовому хранилищу Moto.

```sh
export DB_URL=jdbc:postgresql://127.0.0.1:5433/betaclimb DB_SCHEMA=betaclimb
export DB_USERNAME=betaclimb DB_PASSWORD=betaclimb
export S3__ENDPOINT_URL=http://127.0.0.1:5005 S3__REGION_NAME=us-east-1
export S3__BUCKET_NAME=betaclimb S3__ACCESS_KEY=localtest S3__SECRET_KEY=localtest
```

3. Создайте бакет при первом запуске Moto. Из `backend/worker` выполните `poetry run python -c 'from service.storage import ObjectStorage; s = ObjectStorage(); s.client.create_bucket(Bucket=s.bucket)'`.
4. Запустите Java API из `backend/api` командой `./gradlew bootRun` с JDK 25. Flyway подготовит локальную схему. Из `backend/worker` запустите `ENV_FILES=../../.env MODELS_DIR=../../frontend/ratpoc/assets/models poetry run python -m core.worker`. В этом режиме из корневого `.env` берутся настройки модели, а экспортированные переменные задают рабочие БД и бакет.
5. В `frontend` выполните `npm ci`, затем `npm run dev -- --host 127.0.0.1`. Откройте [локальный интерфейс разработки](http://127.0.0.1:5173/app?source=home). Чтобы сменить хранилище, один и тот же адрес S3 и бакет нужно задать и API, и воркеру.

## Проверка в браузере

Откройте [приложение](http://localhost:5174/app?source=home) в браузере на компьютере. [Главная страница](http://localhost:5174/) показывает лендинг. Порт Compose привязан к loopback компьютера.

Создайте профиль и загрузите один ролик длительностью до 60 секунд и размером до 250 МБ. Подойдёт `frontend/ratpoc/assets/clips/p3_orange.mp4` после скачивания набора. API записывает оригинал в S3 и ставит первую задачу в PostgreSQL. Воркер нормализует видео, выделяет зацепки и их маски, отслеживает 2D-позу, сопоставляет конечности с зацепками и оценивает трассу. Модель получает наблюдаемые эпизоды и материалы по технике. Разбор содержит до трёх советов, для каждого доступны интервал видео и источник. При нехватке данных результат может содержать только ограничения съёмки.

История попыток и воспроизведение привязаны к профилю и cookie браузера. API проверяет владельца и выдаёт временную подписанную ссылку на видео сроком на 15 минут. Бакет сохраняет приватные права доступа. Для повторного просмотра используйте тот же браузер.

## Как изменить разбор

Каждый из восьми этапов очереди — отдельная периодическая задача в [core/tasks](backend/worker/src/core/tasks). Класс этапа объявляет `inputs` — этапы, чьи результаты он читает, — и берёт из очереди только свои строки, когда все входы готовы. Общий цикл запуска задан в [IntervalTask](backend/worker/src/core/tasks/interval_task.py), захват строки, аренда и публикация — в [StageTask](backend/worker/src/core/tasks/stage_task.py), а зависимости воркера собирает [core/worker.py](backend/worker/src/core/worker.py). Период опроса и число параллельных циклов задаются для этапа через окружение, например `TRACK_POSE_TASK__PERIOD=2`. После нормализации видео могут параллельно выполняться поиск зацепок и отслеживание позы. Маски зацепок и координаты конечностей сопоставляются по времени. Затем воркер оценивает цвет трассы, собирает наблюдения за весь пролаз и передаёт их модели. Асинхронный [DBManager](backend/worker/src/database/manager.py) распределяет задачи через PostgreSQL, используя [типизированные модели SQLAlchemy](backend/worker/src/database/models.py). Структуру таблиц задают миграции Flyway, общие для Java API и воркера.

Ожидания от тренера, ограничения ракурса и формат ответа задаёт [системный промпт](backend/worker/src/service/prompts/climbing_coach.ru.md). [Библиотека техники](backend/worker/src/service/knowledge/climbing.ru.json) содержит принципы и реестр публикаций. Для каждого принципа указаны фаза движения, условия применения, видимый признак, альтернативное объяснение и ограничения камеры. Можно добавить принцип и его источники в JSON без изменений в коде. LLM выбирает эпизод, интерпретацию и упражнение по данным конкретного видео. Идентификаторы принципов связывают объяснение с публикациями.

## Что проверяют тесты

```sh
# Из backend/worker
poetry run python -m unittest discover -s tests -v
```

Тесты воркера проверяют длительность видео, видимость движений, формат ответа LLM и привязку советов к исходным наблюдениям. Тестовые HTTP-вызовы используют локальный транспорт. Чтобы включить интеграционные тесты очереди, задайте `BETA_TEST_DATABASE_URL` со строкой подключения к тестовому PostgreSQL. Тесты создают временные схемы, применяют миграции, проверяют конкурентный захват, повтор задачи и публикацию результата, затем удаляют свои схемы. Для сквозной проверки через браузер нужны запущенный воркер, доступные PostgreSQL, S3 и Eliza.

На контрольных видео The Way Up воркер определил цвет трассы в трёх из восьми новых записей. В пяти случаях данных оказалось недостаточно. Для оценки контакта отдельно сверяются конечность, зацепка и интервал. Для проверки советов по технике есть офлайн-инструмент сравнения с комментариями тренеров из Ego-Exo4D. Для съёмки предпочтительны одна видимая фигура и неподвижная камера.
